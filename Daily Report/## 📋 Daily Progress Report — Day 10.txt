## Story 10 — Error Handling & Rate Limiting
**Epic:** epic-2 backend | **Priority:** Medium | **Points:** 2 | **Estimate:** 1 day

---

### What I Did

Today I built a robust error handling and rate limiting system for the AI Code Mentor backend. The goal was to make the API handle failures gracefully so the app never crashes on LLM errors or abusive usage.

**Rate Limiter Middleware** — I installed `express-rate-limit` and created `middleware/rateLimiter.js` with two separate rate limiters. The chat rate limiter allows a maximum of 20 requests per minute per user. If exceeded it returns a friendly `429` status with a clear message telling the user to wait before trying again. The auth rate limiter is stricter, allowing only 10 login attempts per 15 minutes to protect against brute force attacks. Both limiters return structured JSON responses instead of generic server errors.

**Request Logger Middleware** — I created `middleware/logger.js` which logs every incoming request with a timestamp, HTTP method, URL, and user ID. When a response has an error status (400 or above) it also logs the full error details. This gives full visibility into what is happening in the server at all times and makes debugging much easier.

**Centralized Error Handler** — I created `middleware/errorHandler.js` which acts as a global catch-all for any unhandled errors in the application. It handles three specific error types intelligently. LLM timeout errors return a `504` status with a message telling the user the AI took too long to respond. Rate limit and quota exceeded errors return a `429` status with a message about high usage. Authentication errors return a `401` status. Any other unexpected errors return a generic `500` status with a friendly message. All errors are logged with timestamp and user ID for debugging.

**LLM Timeout Handling** — I updated `services/llm.service.js` to wrap all Claude API calls with a 30 second timeout using `AbortController`. If the AI takes longer than 30 seconds to respond the request is automatically cancelled and a timeout error is thrown. This prevents the server from hanging indefinitely on slow API responses. The streaming endpoint also handles timeouts gracefully by sending an error message through the stream before closing the connection.

**App Integration** — I updated `app.js` to wire everything together. The logger runs on every request, the rate limiters are applied to the chat and auth routes specifically, and the error handler sits at the very bottom of the middleware stack to catch any errors that bubble up from the routes.

---

### How the Error Flow Works

```
Request comes in
      ↓
Logger records it
      ↓
Rate limiter checks limit
      ↓ (if over limit)
Returns 429 friendly message
      ↓ (if within limit)
Route handler runs
      ↓ (if error occurs)
Error bubbles up to errorHandler
      ↓
Error logged with timestamp
      ↓
Friendly error returned to user
```
